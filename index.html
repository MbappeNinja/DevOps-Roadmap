Linux & Shell Scripting

The foundation of DevOps
0/6 ▼

Linux is the backbone of DevOps. Almost all servers, containers, and cloud instances run Linux. You need to be comfortable navigating the terminal and writing shell scripts.

File System & Navigation

Learn ls, cd, pwd, mkdir, rm, cp, mv. Understand the Linux directory structure (/etc, /var, /home, /usr).

# List files with details
ls -la /var/log/

# Create nested directories
mkdir -p projects/devops/scripts

# Find files by name
find / -name "*.conf" -type f 2>/dev/null

Users, Groups & Permissions

Understand chmod, chown, chgrp. Learn about file permission bits (read, write, execute) and octal notation (755, 644).

# Change file permissions
chmod 755 script.sh     # rwxr-xr-x
chmod u+x deploy.sh     # Add execute for owner

# Change ownership
chown www-data:www-data /var/www/html

# View current user & groups
whoami && groups

Process Management

Manage running processes with ps, top, htop, kill, systemctl. Understand foreground vs background processes.

# View running processes
ps aux | grep nginx

# Monitor system resources
top -o %MEM

# Manage services with systemd
sudo systemctl start nginx
sudo systemctl enable nginx
sudo systemctl status nginx

Networking Basics

Understand IP addresses, ports, DNS. Use curl, wget, netstat, ss, ping, traceroute, nslookup.

# Check open ports
ss -tulnp

# Test connectivity
ping -c 4 google.com

# Make HTTP requests
curl -s https://api.github.com/users/octocat | jq .

# DNS lookup
nslookup example.com

Shell Scripting (Bash)

Write automated scripts with variables, loops, conditionals, functions, and piping. This is essential for automating repetitive tasks.

#!/bin/bash
# Automated backup script

BACKUP_DIR="/backups/$(date +%Y%m%d)"
mkdir -p "$BACKUP_DIR"

for dir in /var/www/*/; do
    site=$(basename "$dir")
    echo "Backing up $site..."
    tar -czf "$BACKUP_DIR/${site}.tar.gz" "$dir"
done

echo "✅ Backup complete! Files in $BACKUP_DIR"

Text Processing & Piping

Master grep, sed, awk, sort, uniq, cut, wc. Learn to chain commands with pipes (|).

# Find errors in logs
grep -i "error" /var/log/syslog | tail -20

# Count unique IPs in access log
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# Replace text in files
sed -i 's/old-server/new-server/g' config.yml

Git & Version Control

Collaborate and track changes
0/5 ▼

Git is the universal version control system. Every DevOps workflow starts with code, and Git is how teams collaborate, review, and track changes.

Git Fundamentals

Understand repositories, commits, staging area, and the basic workflow: init → add → commit → push.

# Initialize and first commit
git init
git add .
git commit -m "Initial commit"

# Connect to remote
git remote add origin https://github.com/user/repo.git
git push -u origin main

# Check status and history
git status
git log --oneline --graph

Branching & Merging

Create feature branches, merge changes, resolve conflicts. Understand the difference between merge and rebase.

# Create and switch to feature branch
git checkout -b feature/add-login

# Make changes and commit
git add . && git commit -m "Add login page"

# Merge back to main
git checkout main
git merge feature/add-login

# Delete merged branch
git branch -d feature/add-login

Git Workflows

Learn popular workflows: Git Flow (develop/release branches), GitHub Flow (feature branches + PRs), and Trunk-Based Development.

# GitHub Flow (most common)
# 1. Create branch from main
git checkout -b feature/user-auth

# 2. Push and create Pull Request
git push origin feature/user-auth
# → Open PR on GitHub for code review

# 3. After approval, merge PR
# 4. Delete branch, deploy from main

Advanced Git

Master stash, cherry-pick, rebase -i, bisect, reflog. Recover from mistakes and rewrite history safely.

# Stash changes temporarily
git stash && git stash pop

# Interactive rebase (squash commits)
git rebase -i HEAD~3

# Find which commit introduced a bug
git bisect start
git bisect bad HEAD
git bisect good v1.0.0

# Recover lost commits
git reflog

Git Hooks & Automation

Automate tasks with Git hooks: pre-commit linting, commit message validation, pre-push testing. Tools like Husky make this easy.

# .git/hooks/pre-commit
#!/bin/bash
echo "Running linter..."
npm run lint
if [ $? -ne 0 ]; then
    echo "❌ Lint failed. Fix errors before committing."
    exit 1
fi
echo "✅ Lint passed!"

Docker & Containers

Package apps consistently
0/6 ▼

Docker revolutionized how we build, ship, and run applications. Containers package your app with all its dependencies so it runs identically everywhere — "it works on my machine" is no longer an excuse!

Docker Fundamentals

Understand images vs containers, Docker Hub, pulling/running images. A container is a running instance of an image.

# Pull and run an image
docker pull nginx:latest
docker run -d -p 8080:80 --name web nginx

# List running containers
docker ps

# View logs
docker logs web

# Enter a running container
docker exec -it web bash

# Stop and remove
docker stop web && docker rm web

Writing Dockerfiles

Create custom images with a Dockerfile. Learn FROM, COPY, RUN, EXPOSE, CMD, and multi-stage builds for smaller images.

# Multi-stage Dockerfile for a Node.js app
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3000
CMD ["node", "dist/server.js"]

Docker Compose

Define multi-container applications in a single YAML file. Perfect for local development with databases, caches, and app servers.

# docker-compose.yml
version: '3.8'
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=postgres
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine

volumes:
  pgdata:

Volumes & Networking

Persist data with volumes and connect containers with Docker networks. Understand bridge, host, and overlay network modes.

# Create and use a volume
docker volume create mydata
docker run -v mydata:/data nginx

# Create a custom network
docker network create mynet
docker run --network mynet --name api myapi
docker run --network mynet --name db postgres

# Containers on same network can reach
# each other by name: http://api:3000

Image Registry & Tags

Push images to Docker Hub, GitHub Container Registry (GHCR), or private registries. Tag images for versioning.

# Build and tag an image
docker build -t myapp:1.0.0 .
docker tag myapp:1.0.0 ghcr.io/user/myapp:1.0.0

# Push to registry
docker login ghcr.io
docker push ghcr.io/user/myapp:1.0.0

# Pull on production server
docker pull ghcr.io/user/myapp:1.0.0

Docker Best Practices

Use non-root users, minimize image size, scan for vulnerabilities, use .dockerignore, and avoid storing secrets in images.

# Security best practices in Dockerfile
FROM node:20-alpine

# Don't run as root
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app
COPY --chown=appuser:appgroup . .
RUN npm ci --production

USER appuser
CMD ["node", "server.js"]

# Scan for vulnerabilities
# docker scout cves myapp:latest

CI/CD Pipelines

Automate build, test & deploy
0/5 ▼

CI/CD (Continuous Integration / Continuous Delivery) automates the process of testing and deploying code. Every push triggers automated builds, tests, and deployments — catching bugs early and shipping faster.

CI/CD Concepts

CI = automatically build & test on every commit. CD = automatically deploy passing builds. Together they create a fast, reliable release pipeline.

Pipeline stages:

1. 📥 Source    → Code pushed to Git
2. 🔨 Build     → Compile / bundle the app
3. 🧪 Test      → Run unit, integration, e2e tests
4. 📦 Package   → Build Docker image / artifact
5. 🚀 Deploy    → Push to staging → production

Key metrics:
- Deployment frequency
- Lead time for changes
- Mean time to recovery (MTTR)
- Change failure rate

GitHub Actions

The most popular CI/CD platform for GitHub repos. Define workflows in YAML files under .github/workflows/.

# .github/workflows/ci.yml
name: CI Pipeline
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
      - run: npm run build

  deploy:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - run: echo "Deploying to production..."

Jenkins

A self-hosted, open-source automation server. Highly extensible with plugins. Uses Jenkinsfile for pipeline-as-code.

// Jenkinsfile (Declarative Pipeline)
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh 'npm ci'
                sh 'npm run build'
            }
        }
        stage('Test') {
            steps {
                sh 'npm test'
            }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps {
                sh './deploy.sh'
            }
        }
    }
    post {
        failure {
            slackSend "Build failed! 🔥"
        }
    }
}

Automated Testing

Integrate testing into your pipeline: Unit tests (fast, isolated), Integration tests (component interactions), E2E tests (full user flows).

# Testing pyramid in CI:

    /  E2E Tests  \    ← Slow, few
   / Integration   \   ← Medium
  /   Unit Tests    \  ← Fast, many

# Run in parallel for speed:
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps: [...]

  integration-tests:
    runs-on: ubuntu-latest
    services:
      postgres: ...
    steps: [...]

Artifacts & Environments

Manage build artifacts, environment variables, secrets, and deployment stages (dev → staging → production).

# Using secrets in GitHub Actions
env:
  DATABASE_URL: ${{ secrets.DATABASE_URL }}
  API_KEY: ${{ secrets.API_KEY }}

# Multi-environment deployment
deploy-staging:
  environment: staging
  steps:
    - run: deploy --env staging

deploy-production:
  environment: production
  needs: deploy-staging
  steps:
    - run: deploy --env production

Kubernetes

Orchestrate containers at scale
0/5 ▼

Kubernetes (K8s) is the industry standard for container orchestration. It automatically manages deployment, scaling, and networking of containerized applications across clusters of machines.

K8s Architecture

Understand the control plane (API server, etcd, scheduler, controller manager) and worker nodes (kubelet, kube-proxy, container runtime).

K8s Cluster Architecture:

┌─────── Control Plane ───────┐
│  API Server ← kubectl       │
│  etcd (state store)          │
│  Scheduler (place pods)      │
│  Controller Manager          │
└──────────────────────────────┘
         │
┌────── Worker Nodes ─────────┐
│  kubelet → runs pods         │
│  kube-proxy → networking     │
│  Container Runtime (containerd)
└──────────────────────────────┘

Pods, Deployments & Services

Pod = smallest unit (one or more containers). Deployment = manages pod replicas. Service = stable network endpoint.

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: myapp:1.0.0
        ports:
        - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 3000
  type: LoadBalancer

kubectl Commands

The CLI tool to interact with your cluster. Apply manifests, check status, debug issues, and manage resources.

# Apply a manifest
kubectl apply -f deployment.yaml

# View resources
kubectl get pods -o wide
kubectl get services
kubectl get deployments

# Debug a pod
kubectl describe pod web-app-xxxx
kubectl logs web-app-xxxx -f
kubectl exec -it web-app-xxxx -- sh

# Scale up/down
kubectl scale deployment web-app --replicas=5

ConfigMaps, Secrets & Ingress

Manage configuration and secrets separately from code. Use Ingress for HTTP routing and TLS termination.

# ConfigMap for environment config
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "postgres-service"
  LOG_LEVEL: "info"
---
# Secret for sensitive data
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
data:
  DB_PASSWORD: cGFzc3dvcmQxMjM=  # base64
---
# Ingress for HTTP routing
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  rules:
  - host: myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80

Helm & Package Management

Helm is the "package manager" for Kubernetes. Use charts to template and deploy complex applications with a single command.

# Install a chart from a repository
helm repo add bitnami https://charts.bitnami.com
helm install my-redis bitnami/redis

# Create your own chart
helm create my-chart

# Install with custom values
helm install myapp ./my-chart \
  --set replicas=3 \
  --set image.tag=1.0.0

# Upgrade a release
helm upgrade myapp ./my-chart -f production.yaml

# Rollback if something goes wrong
helm rollback myapp 1

Cloud Platforms

AWS, GCP & Azure essentials
0/5 ▼

Cloud computing lets you rent servers, databases, and services on-demand instead of buying hardware. The "big three" are AWS, Google Cloud (GCP), and Azure — they all offer similar core services.

Cloud Fundamentals

Understand IaaS vs PaaS vs SaaS, regions & availability zones, and the shared responsibility model.

Cloud Service Models:

IaaS (Infrastructure as a Service)
→ You manage: OS, runtime, app
→ Example: EC2, Compute Engine, Azure VMs

PaaS (Platform as a Service)
→ You manage: App code only
→ Example: App Engine, Elastic Beanstalk, Azure App Service

SaaS (Software as a Service)
→ You manage: Nothing (just use it)
→ Example: Gmail, Slack, Salesforce

Serverless (FaaS)
→ You manage: Individual functions
→ Example: Lambda, Cloud Functions, Azure Functions

Compute Services

Virtual machines (EC2/GCE), containers (ECS/GKE/AKS), and serverless functions (Lambda/Cloud Functions).

# AWS - Launch an EC2 instance
aws ec2 run-instances \
  --image-id ami-0abcdef1234 \
  --instance-type t3.micro \
  --key-name my-key

# GCP - Create a Compute Engine VM
gcloud compute instances create my-vm \
  --zone=us-central1-a \
  --machine-type=e2-micro

# AWS Lambda function
aws lambda create-function \
  --function-name hello \
  --runtime nodejs20.x \
  --handler index.handler

Storage & Databases

Object storage (S3/GCS), block storage (EBS), managed databases (RDS/Cloud SQL), and NoSQL (DynamoDB/Firestore).

# AWS S3 - Upload files
aws s3 cp ./backup.tar.gz s3://my-bucket/backups/
aws s3 sync ./dist s3://my-website --delete

# Create an RDS database
aws rds create-db-instance \
  --db-instance-identifier mydb \
  --engine postgres \
  --master-username admin \
  --master-user-password secret123

# GCP Cloud Storage
gsutil cp ./data.csv gs://my-bucket/

Cloud Networking

VPCs, subnets, security groups, load balancers, DNS (Route 53 / Cloud DNS), and CDNs (CloudFront / Cloud CDN).

# AWS VPC & Security Group
aws ec2 create-vpc --cidr-block 10.0.0.0/16

aws ec2 create-security-group \
  --group-name web-sg \
  --description "Allow HTTP/HTTPS"

aws ec2 authorize-security-group-ingress \
  --group-name web-sg \
  --protocol tcp \
  --port 443 \
  --cidr 0.0.0.0/0

# Create a load balancer
aws elbv2 create-load-balancer \
  --name my-alb \
  --type application

IAM & Security

Identity & Access Management — control who can access what. Follow the principle of least privilege.

# AWS IAM - Create a policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}

# Best practices:
# ✅ Use IAM roles, not access keys
# ✅ Enable MFA for all users
# ✅ Rotate credentials regularly
# ✅ Use least privilege principle

Infrastructure as Code

Terraform, Ansible & more
0/5 ▼

Infrastructure as Code (IaC) means managing servers, networks, and cloud resources through code files instead of clicking around in web consoles. This makes infrastructure reproducible, version-controlled, and reviewable.

IaC Concepts

Understand declarative (describe desired state) vs imperative (describe steps). Key benefits: consistency, speed, auditability.

IaC Tools Comparison:

Terraform  → Declarative, multi-cloud, HCL
Ansible    → Imperative/Declarative, agentless, YAML
Pulumi     → Declarative, uses real languages (TS/Python)
CloudFormation → AWS-only, declarative, JSON/YAML

Choose based on:
- Multi-cloud? → Terraform or Pulumi
- Config management? → Ansible
- AWS only? → CloudFormation or Terraform
- Prefer real code? → Pulumi

Terraform

The most popular IaC tool. Write HCL (HashiCorp Configuration Language) to define cloud resources. Supports AWS, GCP, Azure, and 1000+ providers.

# main.tf - Deploy a web server on AWS
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234"
  instance_type = "t3.micro"
  
  tags = {
    Name = "web-server"
    Env  = "production"
  }
}

resource "aws_s3_bucket" "assets" {
  bucket = "my-app-assets"
}

# Commands:
# terraform init      ← download providers
# terraform plan      ← preview changes
# terraform apply     ← create resources
# terraform destroy   ← tear down everything

Ansible

Agentless configuration management via SSH. Write YAML playbooks to configure servers, install software, and manage applications.

# playbook.yml - Configure a web server
---
- hosts: webservers
  become: yes
  tasks:
    - name: Install Nginx
      apt:
        name: nginx
        state: latest

    - name: Copy website files
      copy:
        src: ./dist/
        dest: /var/www/html/

    - name: Start Nginx
      service:
        name: nginx
        state: started
        enabled: yes

    - name: Open firewall port
      ufw:
        rule: allow
        port: '80'

# Run: ansible-playbook -i inventory playbook.yml

State Management

Terraform tracks resource state in a state file. Store it remotely (S3, GCS) for team collaboration and use locking to prevent conflicts.

# Remote state backend (S3 + DynamoDB)
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

# State commands:
# terraform state list    ← show all resources
# terraform state show    ← inspect a resource
# terraform import        ← import existing infra
# terraform state mv      ← rename resources

Modules & Best Practices

Organize Terraform code into reusable modules. Use workspaces for environments, and follow a consistent directory structure.

# Project structure
├── modules/
│   ├── vpc/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── web-server/
│       ├── main.tf
│       └── variables.tf
├── environments/
│   ├── dev/
│   │   └── main.tf
│   └── prod/
│       └── main.tf

# Using a module
module "vpc" {
  source = "./modules/vpc"
  cidr   = "10.0.0.0/16"
  env    = "production"
}

Monitoring & Logging

Observe, alert & debug
0/5 ▼

You can't fix what you can't see. Monitoring and observability give you real-time insights into your application's health, performance, and errors. The three pillars are: Metrics, Logs, and Traces.

Three Pillars of Observability

Metrics = numbers over time (CPU, latency). Logs = event records. Traces = request journey across services.

The Three Pillars:

📈 METRICS (What's happening?)
   → CPU usage, request rate, error rate
   → Tools: Prometheus, Datadog, CloudWatch

📝 LOGS (What happened?)
   → Application logs, access logs, error logs
   → Tools: ELK Stack, Loki, Fluentd

🔗 TRACES (Where did it happen?)
   → Follow a request across microservices
   → Tools: Jaeger, Zipkin, OpenTelemetry

Prometheus & Grafana

Prometheus collects and stores metrics. Grafana visualizes them in beautiful dashboards. Together, they're the most popular open-source monitoring stack.

# prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'node-app'
    static_configs:
      - targets: ['app:3000']

  - job_name: 'node-exporter'
    static_configs:
      - targets: ['node-exporter:9100']

# PromQL queries in Grafana:
# Request rate:
rate(http_requests_total[5m])

# Error percentage:
rate(http_errors_total[5m]) / rate(http_requests_total[5m]) * 100

# 95th percentile latency:
histogram_quantile(0.95, rate(http_duration_seconds_bucket[5m]))

ELK Stack (Logging)

Elasticsearch stores logs, Logstash processes them, Kibana visualizes them. Modern alternative: Loki + Grafana (lighter weight).

# Structured logging in your app
const log = {
  level: "error",
  message: "Payment failed",
  service: "payment-api",
  userId: "user-123",
  orderId: "ord-456",
  error: "Card declined",
  timestamp: "2024-01-15T10:30:00Z"
};

# Fluentd config to ship logs

  @type tail
  path /var/log/app/*.log
  tag app.logs



  @type elasticsearch
  host elasticsearch
  port 9200

Alerting

Set up alerts to notify your team when things go wrong. Use PagerDuty, Slack, or email. Define alert thresholds based on SLOs (Service Level Objectives).

# Prometheus alerting rules
groups:
- name: app-alerts
  rules:
  - alert: HighErrorRate
    expr: |
      rate(http_errors_total[5m]) 
      / rate(http_requests_total[5m]) > 0.05
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "Error rate above 5%"

  - alert: HighLatency
    expr: |
      histogram_quantile(0.95, 
        rate(http_duration_seconds_bucket[5m])
      ) > 2
    for: 10m
    labels:
      severity: warning
    annotations:
      summary: "P95 latency above 2s"

SRE & On-Call Practices

Site Reliability Engineering (SRE) practices: SLIs, SLOs, SLAs, error budgets, incident response, and post-mortems.

SRE Key Concepts:

SLI (Service Level Indicator)
→ Measurable metric: "99.2% of requests < 200ms"

SLO (Service Level Objective)
→ Target: "99.9% availability per month"

SLA (Service Level Agreement)
→ Contract: "If below 99.9%, customer gets credits"

Error Budget = 100% - SLO
→ 99.9% SLO = 0.1% error budget = 43.2 min/month

Incident Response:
1. Detect (monitoring alerts)
2. Respond (on-call engineer)
3. Mitigate (stop the bleeding)
4. Fix (root cause)
5. Post-mortem (blameless review)
